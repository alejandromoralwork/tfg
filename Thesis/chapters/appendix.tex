\chapter{Batch Clearing Algorithm}
\label{app:algorithm}

The clearing routine implements \eqref{eq:demandsupply} and
\eqref{eq:clearing} by a search over the admissible price grid, followed
by the tie-break cascade and the rationing step of
\Cref{sec:rationing}.

\begin{lstlisting}[language=,caption={Batch clearing, single asset
pair.},label={lst:clearing}]
INPUT : buys B = {(pi_i, q_i)}, sells S = {(pi_j, q_j)},
        tick grid P, tie-break cascade C, rationing rule R,
        previous clearing price p_prev
OUTPUT: clearing price p*, fills F, residual E

1  candidates <- distinct limit prices in B and S, snapped to P
2  for each p in candidates:
3      D(p) <- sum of q_i over buys with pi_i >= p
4      S(p) <- sum of q_j over sells with pi_j <= p
5      V(p) <- min(D(p), S(p))
6  Vmax  <- max over p of V(p)
7  M     <- { p : V(p) = Vmax }              // maximising set
8  if Vmax = 0: return (no clearing, all orders roll over)
9  M     <- argmin over p in M of |D(p) - S(p)|        // cascade 1
10 if |M| > 1: M <- argmin over p in M of |p - p_prev|  // cascade 2
11 if |M| > 1: M <- argmin over p in M of p             // cascade 3
12 p*    <- unique element of M
13 fill all buys with pi_i > p* completely            // inframarginal
14 fill all sells with pi_j < p* completely
15 marginal <- orders with pi = p* on the long side
16 allocate Vmax - (filled inframarginal) among marginal using R
17 E     <- unmatched quantity on the long side
18 apply time-in-force to E: roll over, or cancel
19 return (p*, F, E)
\end{lstlisting}

Steps 1--7 are the line search; the unimodality of $V$ noted in
\Cref{sec:clearing} guarantees that the maximising set is an interval on
the grid. Steps 9--11 are the tie-break cascade: minimise the residual
imbalance, then minimise distance from the auction's own previous
clearing price $p_{\mathrm{prev}}$ (not an external reference — the FBA
has no oracle input, see \Cref{app:config}), then take the lowest price
as a final deterministic tie-break. Step 16 is the only place where the
rationing rule enters, which is why the rule can be swapped without
touching the price computation.

\chapter{Reproducibility}
\label{app:repro}

Every run's checkpoint file records the configuration of
\Cref{tab:config} together with the input source path, the interval
$\tau$, and per-engine running totals, so that a resumed run can be
checked against the run it continues. A per-file input hash and a code
commit hash embedded in the run's own output --- which would let a
result be tied unambiguously to the exact code and data that produced
it, beyond what the configuration and file list already establish ---
are not currently written by the checkpoint format; this is listed here
as a gap worth closing, not implied to already exist. Given identical
input and configuration, an uninterrupted run reproduces byte-identical
output (\Cref{sec:experiments}). The analysis pipeline reads only the
logged CSV output and is shared by both engines, so no metric is
computed by engine-specific code.

\section{Data Verification}
\label{sec:testdata}

\subsection{Binary Record Decoder}

The order-status archive is stored in a packed binary format of 54 bytes per
record. Eleven tests check the decoder against the format specification and
against real data:

\begin{itemize}
  \item the worked example printed in the dataset's own schema document
  decodes to the expected fixed-point value;
  \item prices decode correctly for every number of decimal places present in
  the data (0, 6 and 7), including round-half-up when the source carries one
  more digit than the internal scale holds;
  \item the sign bit of signed prices is honoured: the same magnitude decodes
  to opposite signs when the bit is set and unset;
  \item quantities round to whole units (39.35 to 39, 39.5 to 40);
  \item a hand-assembled record decodes field by field, and the first 54 bytes
  of the real December file are decoded and compared field by field with the
  known-correct row of the dataset's own CSV preview;
  \item a record whose size rounds to zero is discarded rather than passed on;
  \item a plausibility validator accepts a well-formed record and rejects an
  all-zero buffer (timestamp in 1970), timestamps outside the 2020--2035
  window, and status, order-type or time-in-force codes one step beyond their
  documented maximum.
\end{itemize}

\subsection{Text Parser and File Discovery}

A second reader handles the CSV form of the dataset. Eight tests check that
fixed-point prices (\texttt{126.67}, \texttt{127}, \texttt{0.000001}) and
quantities are scaled and rounded correctly, that two known date--time strings
convert to the correct nanosecond epoch, and that one complete real-shaped row
yields the right order id, user id, status, side, price and remaining size.
They also check that a peek at the first timestamp of a file reads only the
first row and rejects a file with the wrong number of columns, and that file
discovery on a directory tree built out of order returns files in
chronological order, with accepted files before rejected files within an hour,
ignores a stray documentation file and unsupported extensions, and accepts a
single file path.

\subsection{Tests on Real Data}
\label{sec:testrealdata}

Four further tests need the real sample files or system tools and are
therefore run separately from the default suite. All four pass.

\begin{itemize}
  \item Streaming a real compressed sample file end to end produces a sensible
  number of bytes, at least six figures of records, an exact accounting
  identity (records seen equal records produced plus records skipped), and a
  first decoded order that matches the first row of the dataset's CSV preview.
  \item The first-timestamp shortcut agrees with the first record of the full
  stream on the same file.
  \item The scan command reproduces the exact totals of an earlier real run over
  the sample directory (3,630,216 records seen, 54,179 skipped, 2 files
  processed), and its three record categories are mutually exclusive and
  exhaustive.
  \item Archive extraction, run against a real compressed archive built with the
  system \texttt{tar} and \texttt{xz} tools, restores the expected files with
  their contents and sizes and deletes the archive afterwards.
\end{itemize}

\subsection{Time Grid and Coverage}

Coverage is the whole month with no gap: 744 hourly files, first record on
30~November 2025 at 23:59:59.87 UTC and last record on 31~December at
23:59:59.48 UTC. Both engines write one output row for every one-second bucket
from the first record on, empty buckets included, giving exactly
$2{,}678{,}400 = 31 \times 86{,}400$ rows each. The analysis merges the two
files one to one on the bucket start time and stops with an error if the row
counts differ or a row is lost or duplicated in the merge; it never did.

Late events are accounted for rather than ignored. A metric event that refers
to a bucket that has already been written cannot be stored, so it is counted:
none for the FBA and 2,075 for the CDA out of more than 640 million records
(about 3 in a million), a negligible effect. The count is reported so that the
number of discarded events is known.

\subsection{Data-Quality Observations}

Two properties of the data were examined because they could indicate a
decoding error, and neither does. First, 96.0\% of consecutive records carry an
identical nanosecond timestamp, so the median inter-arrival time is exactly
zero. This is consistent with the node writing several events of one match,
such as both counterparties' fills, as one atomic write, and it is the reason
the mean (4.16\,ms) and the 99th percentile (126.6\,ms) are reported alongside
the median. Second, the mix of records (283.8 million new live orders against 281.8
million cancellations) is what an active order book produces, and no status,
order-type or time-in-force code outside the documented lookup tables occurs;
the plausibility validator above would reject one.

\section{Engine Verification}
\label{sec:testengines}

\subsection{Structural Invariant}

One condition is checked live during every run: a price level is never left in
the CDA book with no orders. It is what the matching loop relies on when it
reads the front of a level, and it is enforced at the point of use. If it were
ever broken, the run would stop at once instead of writing a wrong row. The
run completed without stopping. Financial properties (quantity conservation,
no execution beyond a limit price, no duplicated fill) are not asserted during
the run; they are established by the tests below.

\subsection{Automatic Tests of the Engines}

Six tests concern the CDA book:

\begin{itemize}
  \item bid and ask depth against a hand-computed sequence of resting orders, a
  partial cross, a non-crossing sell, a cancellation and a cancellation of an
  order that does not exist, each step also checked against a naive full scan of
  the book;
  \item price priority first and time priority second, across and within price
  levels, when a market buy sweeps three resting asks;
  \item two same-price orders submitted out of timestamp order are still filled
  by timestamp;
  \item cancelling an order that has already been fully filled is a harmless
  no-op;
  \item a fully filled or fully cancelled price level leaves no empty entry
  behind;
  \item a randomised 500-step sequence of submissions and cancellations, with
  every book accessor (depths, order counts, best bid and ask) compared with an
  independent naive scan after every step.
\end{itemize}

Three tests concern the FBA's demand and supply schedules, which are evaluated
by prefix sums and binary search for speed: agreement with a linear-scan
reference exactly at boundary prices for a mixed batch of limit and market
orders; correct behaviour for an empty batch and for an all-market batch, at
the lowest and highest possible price; and a randomised comparison over 200
batches with 20 query prices each. These are differential tests: they show
that the fast implementation equals a simple one, which is the correct way to
verify an optimisation whose specification is the simple version.

\subsection{Hand-Computed Scenarios: CDA}

Fifteen scenarios, each on a fresh book, are compared with values worked out by
hand:

\begin{enumerate}
  \item a resting order with no cross stays in the book;
  \item a cross of exactly equal quantity;
  \item a partial fill of a larger resting order;
  \item a multi-fill sweep that walks two price levels;
  \item price priority beats time priority;
  \item time priority (first in, first out) at the same price;
  \item a market order trades at the resting maker's own price;
  \item a market order with no liquidity neither trades nor rests;
  \item a market order that finds only part of its quantity yields a fill rate
  of 0.8 and not 1.0;
  \item a status row that is not a live order is filtered out entirely;
  \item a sell crosses a resting bid only at or below the bid price, never
  above it;
  \item a cancellation removes the matching resting order;
  \item cancelling an unknown order id is harmless;
  \item a row with status ``filled'' never touches a resting order, because
  fills are outputs of the matching and are not replayed as input;
  \item one complete scenario whose quoted spread, book imbalance and fill rate
  are computed by hand.
\end{enumerate}

Items 9 and 11 (and, in the command parser, the decimal price and quantity
test) are regression tests written after real defects were found; each fails
on the faulty version.

\subsection{Hand-Computed Scenarios: FBA}

Fourteen scenarios, each on a fresh batch engine:

\begin{enumerate}
  \item clearing an empty batch returns no clearing;
  \item a simple full match;
  \item price-time rationing when one side outweighs the other (the worked
  example of the design chapter, run as a test);
  \item a market order is only queued when submitted and trades at the clear, at
  the volume-maximising uniform price;
  \item a tie with no price history picks the lower candidate price;
  \item a batch of only market orders with no price history keeps every order
  instead of losing it;
  \item a batch of only market orders with stale clearing-price history still
  rolls over and is not priced from that history;
  \item a non-live status row is filtered out;
  \item a cancellation removes the matching pending order;
  \item cancelling an unknown order id is harmless;
  \item a ``filled'' row never touches a pending order;
  \item the residual of a partially filled batch rolls into the next batch;
  \item a full metrics scenario after a partial clear (unexecuted residual
  share, fill rate, depth at best, and no quoted spread because the sell side
  cleared completely);
  \item a tie with price history correctly moves the winner to the price closer
  to the previous clearing price.
\end{enumerate}

Item 6 is another regression test for a real defect. Items 5 and 14 together
exercise both branches of the third tie-breaking step of the clearing cascade,
and items 3 and 12 exercise the rationing rule and the roll-over of the
residual, the two design choices on which the results depend most.

\section{Metric Verification}
\label{sec:testmetrics}

The metric code is tested at two levels. Seventeen automatic tests each isolate
one formula or one mechanism:

\begin{itemize}
  \item \textbf{Boundary concentration:} a hand-computed fraction from six
  messages and one batch clear; exact inclusive and exclusive behaviour at the
  edges of the final window; no value for a zero-width batch; and a randomised
  comparison of 200 trials against a naive nested-loop count.
  \item \textbf{Reference prices:} when a book snapshot and a batch clear carry
  the same timestamp the snapshot wins the tie; a markout horizon beyond the last
  available price gives no value.
  \item \textbf{Streaming:} a randomised 140-second CDA stream and an equivalent
  FBA stream, each written incrementally in pieces, produce byte-identical
  output to writing everything at once, including the values carried from one
  piece to the next.
  \item \textbf{Grid and late events:} two snapshots ten buckets apart produce
  all eleven rows in between, with the empty ones empty; a late event for an
  already written bucket is counted, not stored, and does not disturb later
  output.
  \item \textbf{Kyle's lambda:} engineered observations with a true slope of 2.0
  are recovered to within $10^{-9}$ on the CDA and observations with a true
  slope of 125.0 are recovered to within $10^{-6}$ on the FBA; a sweep or batch
  with no net flow or no clearing price is inert; a missing later midpoint gives
  no value; and the FBA carries the previous clearing price correctly across a
  flush.
  \item \textbf{Volatility, Amihud and dispersion:} realized volatility is the
  root of the sum of squared returns and not a standard deviation, with a single
  return reporting its absolute value; Amihud illiquidity has no value in the
  first bucket and the hand-computed absolute return divided by dollar volume in
  the second; price dispersion of two trades at 100 and 102 equals the
  hand-computed relative standard deviation in basis points.
\end{itemize}

Eight further scenarios drive the recorder directly with synthetic events and
compare every reported column with a value computed by hand: the CDA liquidity
and book metrics (spread, depth at best, imbalance, total depth, the three depth
bands, latency and throughput, fill rate); the CDA effective, realized and
impact spreads at the 1, 5 and 30 second horizons together with executed volume
and notional, VWAP, trade count, trader surplus, dispersion and order-to-trade
ratio; volatility and Amihud across two buckets; execution and allocation
metrics for orders that fill partly or never (fill rate, time to execution,
order size inflation); the CDA Kyle's lambda; and the FBA counterparts of the
liquidity metrics (with boundary concentration present and book imbalance and
total depth correctly absent), of the spread metrics (using the unsigned
formulas, since the FBA never sets an aggressor side), and of Kyle's lambda
from net order flow. Together the 37 hand-built scenarios (15 CDA, 14 FBA, 8
metrics) cover the entire metric catalogue of \Cref{app:formulas}.

The remaining automatic tests protect the machinery around the engines: file

\begin{itemize}

\subsection{Relations That Must Hold}

\begin{itemize}
  \item \textbf{Same flow, same volume.} Both engines can only trade against the
  submitted orders, so total executed volume and notional should be almost equal
  and they are: 156.35 million SOL and USD~20.31 billion for the FBA against
  155.57 million SOL and USD~20.20 billion for the CDA (differences of 0.5\%),
  statistically indistinguishable per interval ($p$~=~0.215 and 0.173).
  \item \textbf{Uniform pricing.} Every trade of an FBA batch prints at one price,
  so the FBA's VWAP in a bucket must equal that batch's clearing price and its
  price dispersion must be zero. Dispersion is exactly zero in 96.58\% of the
  buckets where it is defined, and the VWAP identity was confirmed by reading the
  code, where every trade of a clear receives the same price. A bucket that
  contains trades of more than one batch clear can have nonzero dispersion, which
  is why the appendix states the FBA value as approximately zero.
  \item \textbf{Structural emptiness.} Realized volatility, which needs two
  prices in one bucket, has a value in one FBA bucket out of 2,678,400 (against
  2,654,966 for the CDA), as expected from an engine that clears at most once
  per bucket. Metrics that cannot exist for one engine are empty in every row of
  that engine and only there: book imbalance and total book depth for the FBA,
  boundary concentration and unexecuted residual share for the CDA. Pricing
  error is empty in every row of both files, as expected without an oracle.
  \item \textbf{Grid identity.} Both engines have exactly $31\times86{,}400$
  rows, and the merged frame has the same number of rows.
  \item \textbf{Shared activity.} The share of buckets in which both engines trade
  (20.37\%) is nearly four times what independent activity would give (5.53\%),
  consistent with both engines reacting to one order flow and a check that the
  two files are aligned in time.
  \item \textbf{Sign proxy coverage.} All but one of the 545,573 matched buckets
  receive a tick sign (the first has no predecessor).
\end{itemize}

\subsection{Document Consistency}

Every number in the results chapter is generated by the analysis pipeline as a
named macro, so no figure is typed by hand. A script checks that every macro
used in the text is defined in the generated file (230 macros, none missing), and
that every label is unique and every cross-reference resolves. The same
mechanism found and corrected one error during this verification: the share of
skipped records was computed against the wrong base and is now 2.65\% of records
seen.

\section{Coverage, Limits and Reproduction}
\label{sec:testlimits}

The checks above establish that the data are read completely and correctly,
that the engines implement the specified rules on all constructed cases and
behave identically to simple reference implementations on random ones, that
every metric formula returns its hand-computed value, and that the reported
outputs reproduce under independent recomputation. They do not establish
everything, and the gaps are stated here:

\begin{itemize}
  \item the CDA output was not compared trade for trade with the trades
  Hyperliquid's own engine produced from the same flow, so agreement with the
  venue is untested;
  \item the FBA was not run with $\tau \to 0$ to confirm convergence to the CDA,
  which needs the interval sweep that was not run;
  \item determinism follows from the absence of randomness and clocks in the
  engines but the full-month run was not repeated to compare two outputs byte for byte;
  \item neither engine prevents self-trades, and time-in-force is read but not
  enforced, so these behaviours are untested because they are unimplemented;
  \item the update command of the simulator has no tests.
\end{itemize}

All the checks can be repeated. The automatic tests run with
\texttt{cargo test} (76 tests), and the four tests needing real data or system
tools with \texttt{cargo test -- --ignored}, giving 80 passed tests in total.
The 37 hand-built scenarios run with \texttt{market\_sim test engine all}, which
returns exit status 0 only if every scenario passes (15 of 15 CDA, 14 of 14 FBA,
8 of 8 metrics). The record counts come from \texttt{market\_sim scan sol}, the
recomputation of \Cref{tab:testrecompute} from \texttt{analysis/crosscheck\_summary.py},
and the full analysis from \texttt{python analysis/run\_all.py}. All were run for
this thesis with the results reported above.

\section{Bucketing and Notation}

Every column is aggregated into fixed-width time buckets:
\begin{equation}
  \mathrm{bucket}(t) = \mathrm{anchor} + \left\lfloor \frac{t -
  \mathrm{anchor}}{\tau} \right\rfloor \tau,
\end{equation}
where $\mathrm{anchor}$ is the timestamp of the first record of the run
and $\tau$ is the interval (1\,second throughout this thesis,
\Cref{app:config}). Buckets are contiguous and empty-row-inclusive: a
bucket with no qualifying observation still produces a row, so a quiet
period is a gap in the data, not a gap in the file.

A missing value (\emph{None}, an empty CSV field) and an actual zero are
kept distinct and mean different things: \emph{None} is ``no qualifying
observation this bucket,'' zero is ``there were observations and the
value is genuinely zero.'' Every metric below follows this convention
with one deliberate exception, the intra-interval price dispersion
entry of \Cref{sec:formularq22} below. Price- and notional-denominated raw
values are stored in a fixed-point integer scale,
$\mathrm{PRICE\_SCALE} = 10^{6}$; bps and ratio metrics are already
unit-free and are \emph{not} rescaled.

\paragraph{Quoted spread (U).} CDA: for every book snapshot in the
bucket with both sides present and $a_t + b_t > 0$,
$\mathrm{spread}_{\mathrm{bps}} = (a_t - b_t)/\midp \cdot 10^{4}$,
averaged over qualifying snapshots. FBA: for every batch with both a
best unfilled buy and a best unfilled sell and $\clr > 0$,
$(\text{unfilled sell} - \text{unfilled buy})/\clr \cdot 10^{4}$,
averaged over qualifying batches. A snapshot or batch that fails its own
gate is excluded from the mean, not counted as zero.

\paragraph{Depth at best (U).} CDA: mean of (best bid size $+$ best ask
size)$/2$ across snapshots --- touch only, not the whole book. FBA: mean
of (demand at $\clr$ $+$ supply at $\clr$)$/2$ across batches.

\paragraph{Depth within $x$ bps (U), $x \in \{10, 50, 100\}$.} For every
resting order, $\mathrm{bps\_away} = |p - \mathrm{ref}| \cdot
10^{4}/\mathrm{ref}$ against the snapshot midpoint or batch clearing
price; its quantity accumulates into every threshold with
$\mathrm{bps\_away} \le x$ --- the three columns are cumulative, so a
level within 10\,bps also counts toward the 50 and 100\,bps columns.

\paragraph{Book imbalance (C).} $(V^{bid} - V^{ask})/(V^{bid}+V^{ask})$
at the top of book, averaged over snapshots with nonzero touch depth.
Never set on an FBA row --- no code path computes an FBA analogue.

\paragraph{Total book depth (C).} Mean of (bid depth $+$ ask
depth)$/2$ across the \emph{whole} book, every price level both sides
--- contrast with depth at best's touch-only figure.

\paragraph{Effective spread (U), raw per-bucket value.}
\begin{equation}
  \mathrm{dev}_{\mathrm{bps}}(p_k, m_k, D_k) =
  \begin{cases}
    2(p_k - m_k)/m_k \cdot 10^{4} & D_k = \text{buy}\\
    -2(p_k - m_k)/m_k \cdot 10^{4} & D_k = \text{sell}\\
    2|p_k - m_k|/m_k \cdot 10^{4} & D_k \text{ unknown (FBA)}
  \end{cases}
\end{equation}
quantity-weighted per bucket, $m_k$ the pre-trade reference price (CDA:
book midpoint; FBA: the batch's own clearing price). \emph{None} if no
trade in the bucket had a usable reference price. The FBA has no
taker/maker distinction in a uniform-price batch, hence the third case:
every FBA contribution to this raw column is $\ge 0$ by construction (a
mean absolute deviation), while a CDA contribution can be negative (a
fill better than the reference price). This is the value each engine's
simulator writes to its own timeseries CSV; \Cref{ch:results} does not
report the FBA side of it directly, for the reason below.

\paragraph{Signed FBA spread: a CDA-tick proxy.} Comparing the raw FBA
column above to the CDA's genuinely signed one directly would conflate a
measurement asymmetry with an economic one, so \Cref{sec:res21} instead
assigns the FBA a proxy direction before reporting it. The natural
candidate --- classify a batch ``buy'' if its clearing price rose above
the previous batch's clearing price, ``sell'' if it fell --- turns out to
be circular: that previous clearing price \emph{is} $m_k$ in the formula
above, so $\mathrm{sign}(p_k-m_k) \cdot |p_k-m_k| = (p_k-m_k)$, and the
buy/sell sign flip built into $\mathrm{dev}_{\mathrm{bps}}$ exactly
cancels the classification that produced it; no information is added
over the unsigned value. The construction actually used instead ticks
off the \emph{CDA's} price series --- independent of the FBA's own
reference price, since the CDA and FBA are the same order flow processed
two different ways: over the intersection of buckets where both engines
traded (\Cref{sec:res22} gives the exact count), a Lee--Ready zero-tick
rule \citep{leeready1991} on consecutive CDA prices classifies that
second's FBA batch as buy-side if the CDA ticked up, sell-side if it
ticked down, inheriting the last nonzero tick on a flat CDA price. The
signed FBA value reported in \Cref{ch:results} is then this tick sign
times the raw unsigned column above. This is a proxy for the missing
aggressor flag, not a recovery of it: tick-rule classification is
commonly 80--85\% accurate against ground-truth trade direction even
with true trade-level data, and sourcing the tick from the \emph{other}
engine's price series is a further remove again. It is the best
construction available without modifying the simulator and re-running
the replay.

\paragraph{Realized spread (U), $\Delta \in \{1,5,30\}$\,s.} Same trades
and gate as effective spread, but against the reference price at
$t_k+\Delta$ instead of before the trade, found by a binary search over
the combined, time-sorted series of CDA midpoints and FBA clearing
prices (a book snapshot wins a tie against a batch at the identical
timestamp). \emph{None} for a horizon with no trade whose markout falls
within the retained window. The FBA's raw column is, like effective
spread, a mean absolute price displacement rather than a directional
markout, and grows with $\Delta$ roughly as $\sqrt{\Delta}$ from ordinary
price diffusion rather than a widening adverse-selection cost; the same
CDA-tick construction above is applied to it before
\Cref{ch:results} reports it, using one tick sign per bucket shared
across all three horizons. Signed this way, the growth with $\Delta$
does not appear, consistent with a genuine signed statistic in which
diffusion cancels across roughly balanced favourable and unfavourable
moves rather than accumulating.

\paragraph{Price impact (U), $\Delta \in \{1,5,30\}$\,s.} Effective
spread minus realized spread at the matching horizon --- the
adverse-selection component of the effective spread. \Cref{ch:results}
reports this as signed effective spread minus signed realized spread
(both via the CDA-tick construction above), recomputed rather than
signing the raw, already-differenced column: the raw FBA price impact
column inherits the mean-absolute-deviation character of both its
unsigned inputs and can go negative at longer horizons purely because
the unsigned realized spread outgrows the roughly constant unsigned
effective spread, an artefact of the subtraction, not of adverse
selection reversing sign. Assigned only if both signed terms are
computable for that bucket and horizon.

\paragraph{Amihud illiquidity (U).} From the same combined reference-price
series, $\mathrm{close}$ is the last price observed in a bucket, carried
forward across empty buckets. For a bucket with a close and a computable
prior close $>0$:
\begin{equation}
  \mathrm{ret} = \frac{\mathrm{close}-\mathrm{prev\_close}}{\mathrm{prev\_close}},
  \qquad
  \mathrm{amihud} = \frac{|\mathrm{ret}|}{\mathrm{dollar\_volume}} \cdot 10^{6}
\end{equation}
if the bucket traded nonzero volume, else \emph{None} --- a real price
move on zero volume reports \emph{None}, not $\infty$.

\paragraph{Realized volatility (U).} From the reference-price series,
per bucket, consecutive-pair returns $r_i = (p_{i+1}-p_i)/p_i$
(a pair with a non-positive base price is skipped); the reported value
is $\sqrt{\sum_i r_i^2}$ --- the root sum of squares, the standard
realized-variance estimator, deliberately \emph{not} a standard
deviation about the mean. A single return in the bucket reports
$|r|$ directly. \emph{None} with fewer than two usable points.

\paragraph{Matched-timestamp volatility (U).} Unlike the preceding
per-bucket estimator, this is not a field either simulator exports
directly: it is computed by the Python analysis pipeline
(\texttt{analysis/matched\_volatility.py}) from both engines' \texttt{vwap}
columns jointly, after the fact. Build the intersection $\mathcal{T}$ of
buckets where both engines report a trade that second (\texttt{vwap}
non-\emph{None} on both sides); form consecutive-pair log-returns
$r^{e}_i = \ln\!\big(vwap^{e}_{t_{i+1}}/vwap^{e}_{t_i}\big)$ for
$e \in \{\text{FBA}, \text{CDA}\}$ over the same $t_i \in \mathcal{T}$ for
both engines (a pair with a non-positive price on either endpoint of
either engine is skipped); group by the calendar day of $t_{i+1}$, and
report $\sqrt{\mathrm{mean}_i(r^{e}_i)^2} \cdot 10^{4}$ per engine per
day, in bps. This is a root \emph{mean} of squares, deliberately not the
root \emph{sum} of squares the preceding per-bucket formula uses: a
day's matched-return count varies with how active trading was that day,
so an unnormalised sum would conflate a busier day with a more volatile
one, whereas the mean gives a genuine average-return-magnitude figure
comparable across days and across engines. A day with fewer than 5
matched returns is reported as \emph{None} for both engines rather than
a near-meaningless noisy estimate. Because $\mathcal{T}$ requires a trade
on \emph{both} sides, this statistic is conditional on joint trading
activity --- informative for comparing the two engines head to head on
shared ground, but not an unconditional whole-month volatility estimate
for either one alone.

\paragraph{Matched-timestamp volatility, intraday variant (U).} The same
construction through the consecutive-pair log-returns $r^{e}_i$ above,
without the day-level grouping step: each $r^{e}_i$ is reported directly
as $|r^{e}_i| \cdot 10^{4}$ bps, one observation per matched
consecutive-pair return rather than one per calendar day. This mirrors
the fallback the per-bucket realized volatility formula uses when a
bucket has exactly one usable return (reports $|r|$ directly rather than
a root sum of squares over a single term). Trades the daily RMS's
noise-averaging for full time resolution: $n$ is in the hundreds of
thousands rather than around 31, at the cost of each individual
observation being a single return rather than an average over many.

\paragraph{Intra-interval price dispersion (U).}
From bucketed trade prices, $\mathrm{disp} =
\mathrm{stddev}(\{p_k\})/\mathrm{mean}(\{p_k\}) \cdot 10^{4}$ (population
standard deviation). This is the one column that departs from the
\emph{None}-versus-zero convention stated in \Cref{app:formulas}'s first
section: it reports $0.0$, not \emph{None}, whenever the bucket had at
least one trade but the mean price was non-positive. \emph{None} only
when the bucket had no trades at all. Approximately zero for the FBA by
construction (one clearing price per batch): empirically, exactly $0.00$
in the large majority but not literally all FBA-side buckets
(\Cref{ch:results} reports the exact share for the run behind this
thesis) --- a bucket occasionally contains trades from more than one
batch clear, a rare edge case this appendix states rather than asserting
a stronger guarantee than the implementation actually gives.

\paragraph{Kyle's lambda (U, but built differently per engine).} Per
bucket, the OLS slope through the origin, $\lambda = \sum_i x_i
y_i/\sum_i x_i^2$, in bps per unit of the base asset (not
$\mathrm{PRICE\_SCALE}$-denominated). CDA: one observation per
\emph{sweep} (same-timestamp trades sharing a side and a pre-trade
midpoint, grouped in timestamp order); $x$ is the net signed executed
quantity of the sweep, $y = (m_{\mathrm{post}}-m_{\mathrm{pre}})/
m_{\mathrm{pre}} \cdot 10^{4}$ with $m_{\mathrm{post}}$ the midpoint
5\,s after the sweep --- a fixed horizon, independent of the three
realized-spread horizons above. FBA: one observation per priced batch,
walked in strictly ascending order; $x$ is the batch's net order flow
(submitted buy quantity minus submitted sell quantity, captured before
price selection), $y$ the percentage change in $\clr$ from the previous
priced batch. \emph{None} if $\sum_i x_i^2 = 0$ for the bucket. On this
dataset the CDA value is positive-skewed (buy-side sweeps lift the
midpoint, on average); the FBA value clusters near zero --- a
consequence of the price-selection rule described in
\Cref{sec:environment}, which anchors to the previous clearing price and
is close to impervious to a single batch's flow imbalance, not a defect
in the estimator. \Cref{ch:results} reports both.

\paragraph{Pricing error (X, always empty in this dataset).}
$|\clr - p^{\mathrm{ref}}|$ or $|\midp - p^{\mathrm{ref}}|$ against an
external reference price, in bps. No code path in this implementation ever
assigns this column a value: the December~2025 SOL order-status archive
used here carries no oracle or mark-price feed, and none is
reconstructed elsewhere in the pipeline. Every row of both timeseries
CSVs has this field empty, for the entire month, on both engines --- a
documented, structural gap rather than a result of zero.

\paragraph{Executed volume, executed notional (U).} Plain running sums
over the trade stream: quantity, and quantity $\times$ price in raw
$\mathrm{PRICE\_SCALE}$ units (summed before any division).

\paragraph{VWAP (U).} $\mathrm{executed\_notional}/\mathrm{executed\_volume}$
if the bucket executed nonzero volume, else \emph{None}.

\paragraph{Trade count (U).} A plain count, not \emph{None}-valued,
incremented once per trade.

\paragraph{Fill rate (U).} Bucketed by \emph{each order's own submission
bucket}, not the trade's bucket: $\sum \mathrm{filled\_qty} / \sum
\mathrm{orig\_qty}$ over orders first seen in that bucket. \emph{None} if
no order was first seen in the bucket. Because this thesis's interval is
1\,second and most orders take longer than that to reach their eventual
fill state, this bucketing choice --- not a low overall fill propensity
--- is the main driver of a low average value; \Cref{ch:results} reports
it alongside average time to execution, below, for that reason.

\paragraph{Average time to execution (U).}
For every order with a first fill, $(\text{first\_fill\_ts} -
\text{first\_seen\_ts})/10^{9}$ seconds, bucketed by first-seen time;
mean per bucket, \emph{None} if no order first seen in the bucket ever
received a fill.

\paragraph{Trader surplus (U, a plain value, not \emph{None}-valued).}
Accumulated per trade and per side independently: the buy side (when its
limit price is known) contributes $\max(0, \pi - p_k) \cdot q_k$, the
sell side $\max(0, p_k - \pi) \cdot q_k$ --- clipped at zero, so an
adverse fill never contributes a negative amount. This is realized
price improvement against each side's own submitted limit, in raw
$\mathrm{PRICE\_SCALE}$ units.

\paragraph{Order size inflation (U).} Bucketed by first-seen time,
aggregated per (bucket, participant) as (submitted total, filled total);
a participant contributes $\mathrm{submitted}/\mathrm{filled}$ to the
bucket's mean only when both are strictly positive --- an order that
never filled at all is excluded, deliberately, rather than folded in
through a floor on the denominator, which would let never-traded orders
dominate the statistic rather than genuinely oversized ones.
\emph{None} if no participant in the bucket had a computable ratio.

\paragraph{Order-to-trade ratio (U).} $\mathrm{bucket\_message\_count} /
\mathrm{trade\_count}$; the numerator counts \emph{every} message,
accepted and rejected, so its population does not line up one-to-one
with fill rate's. \emph{None} if the bucket executed no trades.

\paragraph{Boundary concentration (F).} Share of order arrivals landing
in the final 10\% of an FBA batch's own window; a zero-width window
contributes nothing. Numerator and denominator accumulate across every
batch closing in the bucket before dividing. \emph{None} if the bucket
had zero total messages across its batches.

\paragraph{Throughput, clearing latency (U, wall-clock and
non-deterministic across runs and machines).} Throughput:
$\mathrm{bucket\_message\_count} / \sum(\text{measured compute time})$.
Clearing latency: $\sum(\text{measured compute time})/\mathrm{count}$,
where the count is \emph{per submission} for the CDA (one book snapshot,
one timing, per actionable record) but \emph{per batch clear} for the
FBA (one timing per batch) --- the same column name measures two
different granularities of operation depending on engine, a caveat that
matters when \Cref{ch:results} compares the two directly. Neither column
is a claim about market quality; both exist to rule out ``one engine is
just slower'' as an alternative explanation for a measured difference
elsewhere.

\paragraph{Unexecuted residual share (F).} Summed across every batch
closing in the bucket: numerator $\sum |\,\mathrm{demand}(\clr) -
\mathrm{supply}(\clr)\,|$, denominator $\sum
\max(\mathrm{demand}(\clr),\mathrm{supply}(\clr))$. This is the
structural one-sidedness of the schedule \emph{at the clearing price}
within a batch, not the complement of fill rate and not ``the share of
submitted volume left unfilled'' in the everyday sense --- a batch can
match every unit it possibly can ($\min(\mathrm{demand},\mathrm{supply})$
executed in full) and still report a high value here if demand and
supply were far apart in size at $\clr$, which is common when $\tau$ is
short and a batch contains few orders. \emph{None} if the denominator is
zero.

\section{Known Gaps}

The caveats behind pricing error, throughput/latency, price impact, and
Kyle's lambda are each stated where the metric itself is defined above,
not repeated here. The one gap with no home elsewhere in this appendix:
comparing simulated CDA output against the trades Hyperliquid's own
engine actually produced from the same flow, and the $\tau \to 0$
degenerate-parameter convergence check, are both not computed here ---
neither the infrastructure nor the parameter sweep either would require
was built (\Cref{sec:validation}).
